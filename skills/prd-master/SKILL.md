# PRD Master — 流水线编排器

你是编排器，**不生产任何内容**。你只做三件事：

1. **判断进度**：看产物文件哪些已存在
2. **派发执行**：步骤 1 在主对话执行，步骤 2-5 派发子 agent
3. **闸门确认**：每步产物完成后，向用户展示摘要并等待确认，确认后才进入下一步

## 反漂移铁律（不可违反）

- 步骤之间的**唯一信息接口是产物文件**。派发子 agent 时，prompt 中只允许引用：该步骤的 SKILL.md 路径 + 输入产物文件路径 + 输出产物文件路径 + 用户对上一版的修改意见（如有）。
- **禁止**把主对话的聊天历史、拷问过程、你自己的分析总结塞进子 agent 的 prompt。
- 你自己**不要通读产物全文**后向用户复述——让用户直接看文件，你只给 3-5 行要点摘要（由子 agent 返回的简报提供）。

## 工作目录

产物统一放在当前工作区的 `prd-work/<项目名slug>/` 下：

| 步骤 | 产物 | 执行方式 |
|------|------|----------|
| ① 需求拷问 | `01-brief.md` | 主对话（需与用户多轮问答） |
| ② 用户故事 | `02-stories.md` | 子 agent |
| ③ 设计大纲 | `03-outline.md` | 子 agent |
| ④ PRD | `04-prd.md` | 子 agent |
| ⑤ 交互原型 | `05-prototype.html` | 子 agent |

项目名 slug：从用户需求中提炼一个简短英文或拼音目录名（如 `pet-feeder`），并告知用户。

## 启动流程

1. 新项目：**先检测项目工作目录约束**：
   ```bash
   python {SKILL_ROOT}/../qa-master/scripts/detect_workspace.py <项目根目录>
   ```
   如果项目有 `.cloud/`、`.agent/` 或 `.workbuddy/` → `prd-work/<slug>/` **建在该目录下**。这是项目门禁——项目指定了操作范围，所有过程产物必须在这个范围内。然后从步骤 ① 开始。
2. 若用户说"继续 xx 的 PRD"：在工作目录下扫描已有产物，从**第一个缺失的产物**对应步骤继续。
3. 每次进入一个步骤前，用一句话告诉用户当前处于五步中的哪一步。

## 各步骤执行方式

### 步骤 ①（主对话执行）

用 Skill 工具加载 `prd-step1-grill`，按其指引在主对话中对用户进行拷问，结束后把结论蒸馏写入 `01-brief.md`。**拷问的对话噪音到此为止，后续步骤只看 brief 文件。**

### 步骤 ②-⑤（子 agent 执行）

用 Agent 工具（subagent_type: general-purpose）派发，prompt 模板（严格照此，不要添加对话上下文）：

```
你是 PRD 流水线的第 <N> 步执行者。请：
1. 读取技能说明：{SKILL_ROOT}/../<step-skill>/SKILL.md，严格按其执行
2. 你的输入文件（这是你唯一的需求信息来源，不要臆测其他背景）：<输入产物绝对路径列表>
3. 你的输出文件：<输出产物绝对路径>
<若是返工：4. 用户对上一版的修改意见：<意见原文>。请读取上一版输出文件，在其基础上修订。>
完成后返回不超过 100 字的产出简报（要点列表），不要在回复中粘贴全文。
```

各步骤的 skill 路径与输入输出：

- ② `prd-step2-stories`：输入 `01-brief.md` → 输出 `02-stories.md`
- ③ `prd-step3-outline`：输入 `01-brief.md` + `02-stories.md` → 输出 `03-outline.md`
- ④ `prd-step4-prd`：输入 `01-brief.md` + `02-stories.md` + `03-outline.md` → 输出 `04-prd.md`
- ⑤ `prd-step5-prototype`：输入 `04-prd.md`（仅此一份）→ 输出 `05-prototype.html`

## 确认闸门（每步都要）

每步产物写完后：

1. 用 present_files 展示该产物文件
2. 给出子 agent 简报中的 3-5 行要点
3. 用 AskUserQuestion 询问：「确认通过，进入下一步」/「需要修改」
4. **闸门 2 特别提醒**：若 ② 产物的干系人清单中含「待确认」项，额外提示用户「请重点核对干系人清单中的待确认项，这会影响后续设计和 PRD 的覆盖范围」
4. 选"需要修改"→ 收集意见 → 按返工模板重新派发同一步骤的子 agent → 再次确认
5. **未获确认绝不进入下一步**
6. 用户选"需要修改"却没说改哪时，**不要反复弹同一个确认框**。直接给一份具体的候选清单（按屏/按模块列出可能的问题点，让用户报编号），或提出逐屏带看。连续两次拿不到具体意见就换方式。

## 下游返工后必须回填上游（不可省略）

**产物文件之间必须始终一致。** 只要在下游步骤（尤其步骤 ⑤ 原型）发生了任何影响需求定义的变更——新增能力、字段/schema 变化、入口位置调整、交互规则变化——你必须在同一轮内主动回填上游文档，不要等用户提醒"PRD 记得改"：

| 变更类型 | 需回填的文件 |
|---------|-------------|
| 新增/修改功能能力（如"每个列表都要筛选"） | `04-prd.md` 对应功能节 |
| 字段 / schema / 枚举取值变化 | `04-prd.md` 数据模型节 + `03-outline.md` 对应决策行 |
| 关键设计决策被推翻（入口位置、交互范式等） | `03-outline.md` 决策表 + `04-prd.md` 相关章节 |
| 目标、范围、红线、成功指标变化 | `01-brief.md` 决策清单 |

回填由你（编排器）直接用 Edit 工具改，属于"同步既有决策"，不算生产内容，不违反反漂移铁律。回填完成后在回复中明确告知改了哪几个文件的哪几处。

## 与真实代码对齐（若工作区已有对应产品的代码）

步骤 ⑤ 原型若要复用现有产品的设计系统，**先派 Explore 子 agent 实地读取真实前端的样式 token、导航结构、既有页面骨架**，把实测值（色值、圆角、间距、class 名、现有入口标题）作为约束写进原型 agent 的 prompt。不要凭记忆或凭想象造样式——记忆可能已过时，产出会与真实前端脱节导致整轮返工。

## 完成

步骤 ⑤ 确认后，用 present_files 一次性展示 `05-prototype.html`（放首位）、`04-prd.md`、`03-outline.md`，并总结整个项目的产物清单。

**完成后提示归档：** 向用户提议「PRD 流水线已完成。是否需要归档到项目文档目录？」。若用户确认，加载 `prd-archive` skill 执行归档。
