# AI-Native SDLC 治理设计 · 门禁全景与停止规则

> 面试素材 + 复习笔记。对应仓库 `ai-sdlc-skills`（Public）。
> 本文所有引用均为仓库内**真实文件**，非示意图。最后更新：2026-08-22。

## 0. 一句话定位（面试开场用）

「我对开发 AI 套了 **5 道门禁 + 1 道覆盖闸门**：动手前用 G3 置信度（看不懂就打回）和 G2 范围（越界按影响层申诉分级）确认边界；写完用 G1 自检（build/test 过才完成）和 G5 清洁保证质量；炸了用 G4 快照回退兜底；最后用覆盖闸门比对 PRD 的 REQ-ID 防静默漏做。硬度上把确定性部分下沉成脚本机械拦截，易变判断留 AI 自觉——这是『确定性下沉、易变留人』的治理边界。」

## 1. 5 道门禁全景（按 dev 流程时间轴）

| 门禁 | 卡在何时 | 干什么 | 硬/软 | 真实落地 |
|---|---|---|---|---|
| **G3 置信度上报** | 动手**前** | 看不懂的需求不写，列 `pending_requirements` 打回 | 软（AI 判断） | `guardrails/G3-confidence.md`；`request.schema` 的 `pending_requirements` |
| **G2 范围自检 + 申诉** | 动手**前** | 改动不超模块目录；越界按影响层分级，签字放行 | 硬（脚本） | `scripts/scope_check.py` + `appeal_log.yaml` + `G2-scope.md` |
| **G1 自检闭环** | 写完**后** | build+test 过才报完成，不过自己修 | 硬（脚本） | `scripts/self_check.py` |
| **G5 代码清洁** | 提交**前** | 不留死代码/垃圾/冗余注释 | 软（AI 审查） | `guardrails/G5-clean.md` |
| **G4 一键还原** | 炸了**时** | 快照回退到上一干净版本，原版本保留可切回 | 硬（脚本） | `scripts/snapshot.py` + `rollback.py` + `G4-rollback.md` |

### 易混点（面试题常挖）
- **G1 管"跑不跑得通"，不是"功能全不全"**——功能全不全是「覆盖闸门」的活。
- **G3 在动手前（看不懂就不写，谈不上回退）；G4 在动手后（写错了才回退）**。把 G3 记成"提交被拒回退"是记混了，那是 G4。
- **G2 越界不再一刀切**：自动探测影响层（UI 层 / 配置 / 函数依赖），**函数依赖 / 跨模块共享必须 human 签字，AI 自签无效**（`appeal_log.yaml`）。

## 2. 第 6 道：需求覆盖闸门（`dev_gate_check.py`）

前 5 道防"跑不通 / 越界 / 炸了 / 不干净 / 看不懂"，但防不了「**PRD 要 10 条你只做 7 条**」。补这一道：
- 比对 PRD 的 **REQ-ID**（`04-prd.md` 每条功能需求编号）↔ DEV 实现回指的 REQ-ID（`artifact_binding`）。
- 缺口即 `exit(1)` 拦截——堵住"静默漏做 PRD 要求"。
- 与 QA 段 `trace_audit`（也做 REQ 覆盖校验）对齐。

## 3. 机械 vs 软：硬度分层（设计铁律）

| 类型 | 门禁 | 机制 | 为什么这么分 |
|---|---|---|---|
| **机械硬拦（脚本）** | G1 / G2 / G4 / 覆盖闸门 | 确定性逻辑下沉脚本，不过就 `exit(1)` | build 过不过、文件在不在白名单、快照存没存，都能机械判定 |
| **软判断（自觉）** | G3 / G5 | AI 判断 + 产物核对 | "看没看懂""代码干不干净"是易变表达，只能留人 / AI 判断 |

→ 这就是仓库 `README.md` 里那条铁律的落地：**确定性逻辑下沉脚本、易变表达留提示词**。

## 4. 多 Agent 编排的停止规则铁律（本次整改核心）

**根因**：`ai-sdlc-master` 总编排器原只写了"何时继续"，没写"何时停止"——自动调度（子 agent 无人值守）下，子 agent 自己把 `confirmed` 状态位写掉，人工确认节点被跳过，于是大跑特跑。

**修复三件套（已推 GitHub，commit `6fddccb`）**：

1. **显式 Halt 规则（何时必须停）**——以下硬中断点必须 halt 回真人、不得自行续跑：
   `PRD 每步确认` / `DEV 启动前` / `DEV G3 低置信` / `QA gate_2·gate_3` / `phase 边界授权`。
2. **治理规则内联进每次派发 prompt**——子 agent **不读** master 的 `SKILL.md`，只看派发时那段 prompt。所以 halt / 通过 / 返回上一层必须写进**每次派发**的四要素里：
   `【派发方式】` `【停止规则】` `【通过 → 调度下一轮】` `【返回上一层】`。
   （原"集中写一节停止规则"被否——因为子 agent 根本看不到那节。）
3. **auto-confirm 仅主对话模式**——无人值守（自动调度）模式下一律关闭，所有 gate 必须真人 `AskUserQuestion` 确认，AI 不得自签。落在 `qa-master/SKILL.md` + `README.md`。

> 一句话铁律：**继续是默认，停止必须显式声明且内联进派发；auto-confirm 只在真人在场时生效，无人值守一律关。**

## 5. 面试问答预备（可能被追问）

- **Q：G2 一刀切怎么改进的？**
  → 越界自动探测影响层 + `appeal_log.yaml` 签字放行；函数依赖强制 human 签字，AI 自签无效。确定性（层别判定）下沉脚本，易变（放不放行）交人。
- **Q：确认闸门怎么防 AI 自己跳过？**
  → `confirmed` 状态位只能主对话真人回写；auto-confirm 仅主对话模式；无人值守全关。
- **Q：为什么 G3 / G5 不用脚本硬拦？**
  → 它们判的是"AI 老不老实 / 代码干不干净"，无法机械判定，只能靠自觉 + 产物核对。
- **Q：多 agent 怎么保证子 agent 守规则？**
  → 规则内联进派发 prompt（子 agent 不读本 SKILL），而非集中写一节。
